## Setup

- **Leakage split** (`search/adfgvx/lm.py`): the 591 solved plaintexts are linked into components by any shared 16-character substring (so repeated receptions and re-sent messages stay together), and each component goes to TRAIN or PLANT by a seeded coin (seed 20261101). TRAIN: 297 entries, the scorer's only text. PLANT: the rest; only those without unknown marks are planted (F1, F2); F3 uses plant-side as-transcribed entries under their own key. No planted plaintext, and no near-copy of one, is in the scorer's training text.
- **Scorer**: interpolated trigram model on A-Z0-9 (lambdas (0.6, 0.3, 0.09, 0.01)), mean natural-log probability per trigram.
- **Planted clusters (F1, F2)**: a random 36-cell square and a random transposition of the cell's width; one member per member of a real unread group in the cell's letter bin (group drawn uniformly among the bin's groups), each member's plaintext cut from a plant-side plaintext to half the member's letter count.
- **Damage, scaled to the unread set**: one census edit profile per message (types and run lengths from results/adfgvx-mutilation.csv, random positions); E5 at 0.0066/symbol (the repeated-reception rate, not the census-visible one); lost marks topped up to Poisson(0.0566/slot) in runs drawn from the SOLVED log's run lengths; then the parity forced odd with probability 0.354 (one extra deletion where needed).
- **Wrong-day intruders**: each member is, with probability 0.03, enciphered under a different random key (the solved set's heading-date error rate against the DERIVED key ranges, results/adfgvx-clusters.md s.1c). Recovery is measured on the true-key members only.
- **Recovered** (F1, F2): the attack's key decrypts at least 80% of the true-key members' plaintext characters correctly from their UNDAMAGED ciphertexts. (F3: the best variant's decryption has difflib ratio >= 0.8 to the true plaintext.)
- **Widths searched**: 15-22 in every trial, planted and null alike; the attack is not told the width.

### The edit-jump statistic (adversary baseline: a true key jumps on one edit, a wrong key creeps)

J = the largest gain in best score from one more edit: max(best(1 edit) - best(0), best(2 edits) - best(1 edit)), from the cap-2 run; per-trigram natural-log units (the adversary's +2.4-3.7 is in log10 per quadgram, so the numbers differ, the shape is the question). Creep = mean gain per edit.

## Recommendations for the J prereg (proposed, not applied)

1. **Decision statistic and threshold.** Use the penalised trigram score of the final key. Fix the threshold per family and per cluster-letter bin as the maximum over the null trials of that bin (wrong-period and shuffled pooled), exactly as tabulated above. That is about 200 null trials per bin, so 10/alpha holds at alpha = 0.05 per bin. A threshold set at the maximum of n nulls has a false-positive rate of 1/(n+1) for a new null draw (about 0.5% here), per bin and per family; across bins and families these add, and the trials factor must say so. The real run must use the identical pipeline, budget, widths and scorer: any change invalidates the threshold.
1b. **The nulls are optimised.** Every null trial (wrong-period clusters, shuffled clusters, F3 wrong keys and shuffles) runs through the identical solver, budget, widths and edit search as the planted trials, so the thresholds are best-of-optimised-null, as the adversary baseline requires; random-key nulls are not used.
2. **Above threshold is a DETECTION, not a reading.** In the planted runs a single-key cluster can beat every null with a wrong key (tables 'Detection is not reading'). A reading needs a second, pre-registered gate: reproduction by check-adfgvx from method and key, the adversary failing to match, and (proposed) the decryption passing a fixed word-coverage or n-gram criterion calibrated on the 'wrong but above threshold' planted cases above.
3. **Mutilation cap in symbol edits,** by the rule in the last section, searched as at most 2 edits. The rule's M(N) is the 90th percentile in the table there; the search can only reach total costs 0, 1, 2, 5, 6 and 10, so M maps to the smallest reachable cost >= M (M = 3, 4 or 5 all map to 5: one 5-group edit, or up to two single-symbol edits). The symbol-cap table above gives the power at each reachable M. Cap 3 costs ~200x the CPU per message (2.4e7 variants) and showed no gain in its 20-message sample. Edit freedom counts as key bits (A2): the variant counts per message are in the F3 table and belong in the trials factor.
3b. **Edit-jump statistic as a second pre-registered test (adversary baseline).** J > 1.271 (the max over 400 optimised nulls) was reached by 15/110 damaged planted messages; 13 pass both J and the score threshold. It costs nothing extra (same search) and its FP for a new null draw is 1/(n+1). With optimised nulls on THIS scorer it is a weak test: shuffled nulls jump almost as far as true keys (J table), so it should be pre-registered, if at all, as a secondary test with its own null threshold, not as the gate.
4. **Budget.** The F1 search is budget-limited at the larger odd widths, 21 above all. On an undamaged 1,500-letter width-21 cluster, the true order scores 0.104 on the phase-A statistic and the search found only 0.081, so this is a search failure, not missing information (diagnostic run 2026-11-01, not part of the tables). A negative for a width-21 key at this budget is a statement about the method, not the cipher. The prereg should either raise the budget for widths 19-21 and re-run these controls at it, or state that limit.
   The maximum is a fragile statistic where the null tail is thin. Example: when nulls were binned by the composition they were drawn for rather than by their actual letter count, one 256-letter wrong-period null (-2.647) sat in the 300-699 bin and F2's power there fell from 38/160 to 13/160. Bin by ACTUAL letters, as here, and fix the rule (max over the stated nulls) in the prereg; a larger null set per bin would make it steadier.
5. **Small clusters.** Below 300 cipher letters no F1 or F2 result clears its null, and F1 gets nothing below 700. Below 300, only a known key (F3, per message) has power.

## What this does not establish

- **Generality.** Every rate is [S], for this scorer, this budget and this damage model. The scorer is a trigram model on ~30k characters of period text; a larger corpus or quadgrams could raise power.
- **The real damage of the unread entries.** The model is the census plus the lead's two unread summary rates. It has no clerk errors (E6), no keys outside the list (E8), and intruders only at the 3% derived-range rate; the 20.1% published-period rate was not run.
- **The real cluster compositions.** The compositions are the derived groups' letter counts, including entries the duplicate screen (results/adfgvx-duplicates.md) found to be copies of solved messages. Removing those shrinks several groups, which moves them to lower-power bins.
- **Independence.** One implementation (search/adfgvx/jattack.c, power.py). Not reproduced by check-adfgvx.
- **Runtime.** Every number is CPU seconds on a shared 8-core box (load average 25-100 during the runs); wall time is not meaningful.
